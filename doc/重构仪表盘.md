

# EchoAnswer 仪表盘模块重构提示词


你现在需要对 EchoAnswer 项目的「管理控制台 → 仪表盘」进行一次完整的 UI/UX 重构。

重要：这不是简单调整颜色、间距或替换几个 ECharts 图表，而是对现有 Dashboard 进行“信息架构 + 数据表达方式 + 页面布局 + 图表视觉体系”的整体优化。

请严格基于当前项目设计文档、现有 API 和实际代码实现，不要破坏已有功能和数据逻辑。

==================================================
一、项目背景
==================================================

EchoAnswer 是一个 Web 端语音问答展示与多智能体问答平台。

管理控制台当前已经存在 Dashboard 仪表盘，并通过：

GET /api/admin/stats

提供统计数据。

当前 Dashboard 虽然已经实现了：

- 今日提问
- 今日登录
- 在线访客
- 累计提问
- 错误率
- 服务运行时长
- 提问趋势
- 访问趋势
- 活跃时段
- 智能体维度
- 协议维度
- 错误分布
- 运行情况

但目前页面存在明显问题：

1. 图表数量较多，但缺少明确的信息层级。
2. 页面像“数据报表拼盘”，不像一个成熟的管理驾驶舱。
3. 图表之间视觉语言不统一。
4. 大面积深色背景 + 细边框 + 网格线导致页面比较沉重。
5. 图表标题、辅助说明、图例、坐标轴文字过小。
6. 很多图表占据了很大的空间，但实际传递的信息非常少。
7. 饼图、柱图、折线图使用方式比较传统，没有充分利用数据表达。
8. 重要指标没有形成“总览 → 趋势 → 分析 → 明细”的阅读路径。
9. 智能体、协议、错误等数据虽然都有，但没有形成明显的运营分析层级。
10. 空数据、低数据量场景下图表显得尤其空洞。
11. 页面纵向过长，用户需要不断滚动才能看到完整信息。
12. 当前截图中的视觉效果比较像后台开发人员制作的数据页面，而不是经过设计的产品级控制台。

因此，本次任务必须进行整体重构。

==================================================
二、设计目标
==================================================

把 Dashboard 从：

“统计图表页面”

升级成：

“EchoAnswer 管理驾驶舱”。

用户进入 Dashboard 后，应该在 5 秒内知道：

- 当前系统是否正常
- 最近问答量如何
- 用户是否活跃
- 哪个智能体使用最多
- 哪种协议承担主要请求
- 当前是否存在明显错误
- 系统当前运行状态如何

页面阅读顺序必须形成：

【核心指标】
      ↓
【整体趋势】
      ↓
【活跃行为】
      ↓
【智能体 / 协议分析】
      ↓
【异常 / 系统状态】

而不是现在的“一个图表接一个图表”。

==================================================
三、整体视觉方向
==================================================

继续保持项目当前的深色控制台风格，但重新建立视觉设计系统。

关键词：

现代 SaaS
专业管理后台
数据驾驶舱
克制
轻量
高级
信息层级清晰
低视觉噪音

不要做成：

- 大屏数据可视化
- 炫酷科技风
- 发光霓虹风
- 满屏渐变
- 满屏卡片
- 花哨动画
- BI 软件堆图表风格

整体感觉应该接近：

Linear / Vercel / Raycast / Stripe Dashboard / 高级 SaaS Admin

而不是传统 ECharts Demo。

==================================================
五、顶部核心指标重新设计
============

当前顶部 6 张指标卡视觉比较普通，需要重做。

建议保留 5 个核心指标，不要为了“六张卡”而六张卡。

优先：

1. 今日提问
2. 在线访客
3. 期间提问
4. 成功率
5. 平均响应时间

“服务运行时长”不要作为一级核心指标，可以放入右侧“系统状态”。

每张指标卡包含：

* 小标签
* 大数字
* 同比/环比变化
* 简短辅助信息
* 极小型趋势 Sparkline（如果数据支持）

例如：

今日提问
12
↑ 24% vs 昨日

底部显示一个非常轻量的趋势线。

不要使用巨大数字。

不要让每张卡都使用不同颜色。

推荐：

默认文字保持中性；
正向变化使用绿色；
异常使用红色；
主要强调色使用项目当前主题蓝色。

==================================================
六、核心图表：提问趋势
===========

这是整个 Dashboard 最重要的图表。

不要继续使用当前：

“堆叠柱 + 成功率折线 + 双 Y 轴”的传统组合。

重新设计。

推荐：

主图使用：

「面积折线 + 成功率轻量折线」

或者：

「柱状提问量 + 成功率辅助折线」

但视觉上必须以“提问量趋势”为绝对主体。

X轴：

日期。

Y轴：

提问数量。

身份分类：

管理员 / 普通用户 / 访问码 / 匿名

不要默认全部堆叠展示。

建议增加一个轻量的切换：

[全部] [管理员] [用户] [访问码] [匿名]

默认显示：

全部提问趋势。

如果需要查看身份，再通过筛选切换。

这样可以避免一张图同时出现太多颜色。

成功率：

不要让第二 Y 轴抢视觉重点。

可以采用：

* 图表顶部显示“成功率 98.4%”
* 或使用非常细的辅助线
* 或切换指标

核心原则：

“提问趋势是主信息，成功率是辅助信息。”

==================================================
七、访问趋势重新设计
==========

当前“每日登录 + 新建会话”单独作为一张图，信息价值比较有限。

不要继续制作普通双柱图。

将它重新整合到“用户行为”模块。

建议：

标题：

用户活跃

左侧：

登录 / 新建会话趋势

右侧：

当前在线访客

底部：

访问主体构成

使用：

小型趋势图 + 数字指标。

匿名访问没有历史登录统计口径，不要伪造匿名历史数据。

严格使用 /api/admin/stats 实际提供的数据。

==================================================
八、活跃时段
======

当前 0～23 点柱状图太普通。

重新设计成：

「24 小时活跃热力图」

例如：

00 01 02 03 ... 23

用低饱和度深浅表达活跃程度。

或者：

如果当前 ECharts 结构实现热力图成本过高，则使用：

24 小时柱状图 + 峰值标记。

要求：

* 弱化坐标轴
* 隐藏不必要的 Y 轴文字
* 只突出峰值
* Tooltip 显示：
  “15:00 · 3 次提问”
* 峰值使用主题色强调

不要使用当前这种普通 Excel 柱状图效果。

九、智能体维度
=======

这是 EchoAnswer 多智能体架构非常重要的一部分。

不要只做：

“一个横向长条 + 一张表”。

改成：

「智能体使用排行」

左侧：

Top 5 横向条形排行。

每行：

排名
图标
智能体名称
提问数
成功率

右侧：

选中智能体的关键指标：

提问量
成功率
平均响应
最近活跃

如果当前只有一个智能体，也必须设计得好看。

不要因为只有一个数据就拉一根巨大的横条占满半个屏幕。

单智能体情况下：

采用“智能体摘要卡”：

[图标]
行业大脑
industry-brain

9 次提问
100% 成功
8.5s 平均响应
最近活跃：2026-10-06 15:59

并在未来智能体数量增加后自动切换成 Top N 排行。

不要固定使用饼图。

根据数据数量动态选择：

1～2 个协议：

使用横向比例条。

3～5 个协议：

使用横向条形排行。

超过 5 个：

可以使用环形图。

---

○ 未启用

停用协议使用低饱和度灰色，不要大面积红色。

只有真正发生错误时才使用红色。

十一、错误分布

错误分布不要做成一个巨大的普通 Top8 柱状图。

改成：

「系统异常」

如果错误数 = 0：

显示一个非常简洁的健康状态：

✓ 当前暂无异常

不要空图表。

如果存在错误：

显示：

错误数量
错误率

然后列出 Top 5：

错误类型
出现次数
涉及协议
最近发生时间

错误条形图可以保留，但使用紧凑的横向排行。

Tooltip 显示完整错误信息。

十三、页面布局优化
=========

当前页面最大的问题之一是：

每个图表都被放进一个独立的大矩形框。

必须改变。

不要：

┌────────────────────┐
│ 图表                │
│                    │
└────────────────────┘

┌────────────────────┐
│ 图表                │
│                    │
└────────────────────┘

┌────────────────────┐
│ 图表                │
│                    │
└────────────────────┘

而应该形成：

“内容区块”。

减少明显边框。

使用：

* 微弱背景层级
* 轻边界
* 统一圆角
* 合理留白
* 标题层级
* 数据之间的视觉关系

让页面看起来更像一个完整 Dashboard，而不是多个 ECharts 容器。

==================================================
十四、图表视觉规范
=========

建立统一图表视觉语言。

统一：

字体
字号
网格线
Tooltip
图例
坐标轴
圆角
动画
颜色

原则：

1. 网格线极弱
2. 坐标轴尽量隐藏
3. 图例尽量靠近标题
4. 不使用过多颜色
5. 同一数据类型始终使用同一种颜色
6. 正常状态使用主题色
7. 成功使用绿色
8. 错误使用红色
9. 未启用 / 无数据使用灰色
10. 不要每个图表都重新定义一套颜色

建议颜色语义：

Primary：
项目主题蓝

Success：
绿色

Warning：
橙色

Danger：
红色

Neutral：
灰色

但不要把所有指标卡染成彩色。

==================================================
十五、空数据场景必须重新设计
==============

这是本次重构非常重要的一点。

当前截图数据量很少：

例如只有一个智能体、一个协议、部分日期有数据。

这种情况下当前 Dashboard 显得特别“空”。

必须针对低数据量做专门设计。

例如：

智能体只有 1 个：

不要画巨大空白排行榜。

协议只有 ragflow：

不要画巨大环形饼图。

错误为 0：

不要显示一个空图表。

某天没有数据：

不要制造视觉噪声。

应该显示：

“暂无数据”

或者使用轻量状态提示。

Dashboard 必须在：

0 条数据
1 条数据
10 条数据
100 条数据

情况下都保持良好的视觉比例。

十七、时间范围控制
=========

顶部保留：

[近 7 天] [近 14 天] [近 30 天]

但重新设计成紧凑 Segmented Control。

不要占据一整行。

切换后：

调用：

GET /api/admin/stats?days=N&fresh=1

自动刷新：

继续支持当前设计的自动刷新。

默认 60 秒。

页面隐藏时停止自动刷新。

这些已有行为不能破坏。

==================================================
十八、数据逻辑要求
=========

非常重要：

不要修改统计数据的业务定义。

不要为了让图表好看而修改后端统计逻辑。

不要虚构数据。

不要生成不存在的指标。

不要修改：

/api/admin/stats

的数据语义。

优先复用当前 API。

如果某个视觉效果需要新的数据：

先检查现有接口是否已经提供。

只有现有数据确实无法实现时，才提出最小化 API 扩展方案。

本次任务原则上优先只改前端 Dashboard。

继续使用 ECharts。

* 自动 resize

* 避免重复初始化
* 避免内存泄漏
* tooltip 风格统一
* 动画克制

不要为了“高级感”增加大量动画。

### 特别建议注意这一点

从你现在截图看，**最应该砍掉的是“每个统计项一个大图表”的思路**。

设计文档虽然规定了七类统计内容，但并没有要求它们必须以七个独立的大图表呈现。文档实际上只规定了这些统计维度及数据来源，例如提问趋势、访问趋势、活跃时段、智能体、协议、错误和运行情况。:contentReference[oaicite:2]{index=2}

所以这次重构的核心应该是：

> **数据维度不减少，但视觉模块减少。**

例如：

| 现在 | 建议 |
|---|---|
| 提问趋势大图 | **保留，作为主图** |
| 访问趋势大图 | 并入“用户活跃” |
| 活跃时段大图 | 改成热力图/紧凑柱图 |
| 智能体大图 | 改成排行 + 摘要 |
| 协议环形图 | 改成动态横向比例 |
| 错误 Top8 大图 | 改成异常状态模块 |
| 运行情况大表 | 改成实时状态面板 |

这样做之后，Dashboard 会从现在这种：

**“图表很多，但不知道先看什么”**

变成：

**“先看系统状态 → 再看问答趋势 → 再看用户/智能体 → 最后看异常。”**

而且你截图里目前只有 **1 个智能体、1 个有效协议、很少的历史数据**，这种情况下尤其需要动态布局，否则无论 ECharts 做得多漂亮，都会出现“大面积空白”的问题。

项目文档也明确规定了 `/api/admin/stats` 是纯查询聚合、支持 `days=1–90` 和 `fresh=1`，所以这次**完全可以优先做前端 Dashboard 重构，不必动后端统计接口**。:contentReference[oaicite:3]{index=3}
